# 痛点经验内容写作

[English](SKILL.md) | [简体中文](SKILL.zh-CN.md)

使用本 Skill，将已解决的运营、技术、产品、增长或工作流痛点整理成标准方法论草稿，之后可改写到即刻、飞书或其他获准的平台。本 Skill 只负责写内容；不会登录、发布、创建远程文档或改变平台状态。

## 来源约定

只使用当前对话或用户提供材料中已有的事实。整理以下内容：

- 具体痛点及其背景；
- 可观察到的影响或摩擦；
- 尝试过的方法，以及它们失败或不足的原因；
- 最终方案，以及证明方案有效的证据；
- 方案的优势、成本、维护要求、风险和未解决的注意事项。

只有当缺失事实会改变方案或复现过程时，才提出一个简短、具体的问题。不要编造指标、日期、截图、引语、成本、权限或结果。

## 标准输出

按以下顺序返回 Markdown 草稿：

1. 结果先行的标题：`如何让/用 <工具> 实现 <结果>，并且不再 <常见失败>：`
2. 一段简短开场，说明实际问题和结果。
3. 一句原则和一条易记的规则。
4. 两到四个具体用法示例、命令或判断规则。
5. 五到七个编号复现步骤。
6. 一段简短的失败路径或绕路记录。
7. 说明该方案为什么比显而易见的替代方案更稳定。
8. 说明成本、维护、安全和仍未解决的注意事项。
9. 结尾说明工作流如何从旧的手动或易出错方式转变为新的稳定方式。

当内容确实反映作者经历时，使用第一人称。段落要短，信息密度要高。除非用户要求，不要使用“痛点一句话”等字面标签。

## 可移植性与脱敏门槛

在把草稿标记为适合公开之前，先将可迁移的方法与作者的本地环境分开：

- 保留原则、判断规则、通用命令、占位符和验证信号。
- 将个人代理节点、公网 IP、代理端口、主机名、账号名称、组织标识、本机绝对路径、机器专用别名和私有 URL 替换为通用占位符或删去。
- 不要把作者的确切网络路线写成解决方案。改用“使用你获准使用的代理端点”或“设置当前环境所需的代理变量”。
- 具体的个人取值只放在私有本地实现说明中；默认情况下绝不要复制到公开帖文。
- 如果读者必须使用作者的账号、节点、密钥或机器路径才能复现，该方法就不适合公开。

## 复现门槛

返回草稿前，确认读者能回答以下问题：

- 需要哪些前置状态？
- 应该执行哪些准确步骤或命令？
- 哪个信号能证明修复有效？
- 应避开哪些常见失败？
- 采用后应该衡量什么？
- 如果读者只有 30 分钟，最先做什么有用？

如果需要针对特定平台的步骤，就抽象地描述，并把实际的平台变更留给 `jike-painpoint-sync` 执行。

## 公开安全规则

剔除密钥、OAuth 验证码、密码、令牌、私人邮箱、内部 URL、客户名称、非公开账号标识、个人网络节点、公网 IP 和机器专用端口。只有在明确标注为私有实现说明中的占位符时，才允许使用 localhost 端口；公开草稿应使用 `<proxy-port>` 或同类变量。

区分事实、解读和未知。将仍然存在的警告写成注意事项，不要暗示所有诊断警告都已修复。

## 回归样例

提示形式：“把一个已解决的 Claude Code 登录问题写成即刻经验贴，但不要发布。”预期内容包括代理与身份验证的区别、损坏的 shell 封装脚本这一根因、使用占位符且可移植的验证命令；不得包含授权码、私人账号详情、个人节点或机器专用端口。
