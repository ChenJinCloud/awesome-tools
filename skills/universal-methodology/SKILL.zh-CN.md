# 通用方法论

[English](SKILL.md) | [简体中文](SKILL.zh-CN.md)

使用此 Skill 将一个模糊输入推进成经过判断、边界明确、可以执行并能够收束的结构，同时避免把所有事情都过度管理。

v1.2 强调先保证决策质量，再推进执行：不要只是帮助用户更快完成事情。首先检查目标是否正确、默认值是否在驱动它，以及继续推进是否能改善用户未来的位置。

## 运行原则

首先判断这件事是否值得结构化。不要假设每个输入都应该变成任务、交付物或可复用资产。

保持结果达到“80 分有用”：结构足以减少模糊与返工，但不会因结构本身增加摩擦。

优先选择最小但有用的模式：

- 快速诊断：判断事项类型并给出下一次状态跃迁。
- 决策审查：检查默认值、目标正确性、位置影响、选项和保障措施。
- 执行计划：确定下一项具体交付物和推进节律。
- 完整规划：事项较大或涉及大量交接时，使用完整推进卡。
- 收束与采收：决定关闭、归档、提炼方法论、创建 SOP/Skill，或不采取行动。
- 系统方法论提炼：当用户提供笔记、摘录、复盘或案例时，先提炼系统原则和放置决定，再建议行为改变。

## 核心流程

使用以下顺序：

```text
事项收拢 -> 默认值诊断 -> 目标校准 -> 事项定性 -> 边界定义 -> 位置与资源判断 -> 结构设计 -> 协同编排 -> 节律执行 -> 决策质控与交付 -> 收束采收
```

英文标签：

```text
Capture -> Default Check -> Target Calibration -> Orient -> Define -> Position & Resources -> Architect -> Orchestrate -> Execute -> Decision QA & Deliver -> Close & Harvest
```

## 如何回应

1. 收拢事项：名称、来源、为什么现在出现、截止时间、交付对象、已有材料和当前压力。
2. 选择最小但有用的输出模式。除非事项确实需要，或用户明确要求，否则不要使用完整推进卡。
3. 诊断默认值漂移：情绪、自我、社会压力、惯性或身体与精力状态。
4. 校准目标：正在追求什么结果、它是否值得被想要、目标由谁或什么设定，以及什么才算正确结果。
5. 先定性再规划：判断事项类型，并决定推进、延迟、降级、放弃、单纯体验还是采收。
6. 定义边界：目标、当前状态、限制、最低可交付版本、成功标准和不做什么。
7. 检查位置与资源：事项是否改善未来的选择权、缓冲、信任、能力和信息质量；投入的时间、精力、金钱、休息、机会成本或不可逆资源是否合理。
8. 设计工作结构：生命周期阶段、状态链、模块、接口、易返工部分、资源链、风险链和保障措施。
9. 编排责任：AI、工具、用户、其他人以及环境或系统分别负责什么。
10. 按节律执行：条件允许时每轮完成一次状态跃迁；包括耗时、中断点、恢复方式、缓冲和降级路径。
11. 同时质检决定和输出：目标正确性、默认值风险、备选方案、安全系数、过程记录、交付质量、系统成本和下游影响。
12. 主动收束：选择关闭、归档或采收。只有复用价值高于提炼成本时才采收。

## 事项类型

在“事项定性”阶段使用以下类别：

- 建设型事项：需要产出、积累、复利或交付。
- 维持型事项：保持稳定、修复系统或防止失控。
- 探索型事项：收集信息或打开可能性，不急于得出结论。
- 体验型事项：价值存在于体验本身，未必需要资产。
- 关系型事项：优先考虑信任、情绪和协作，而不是效率。
- 恢复型事项：恢复精力、身体、情绪或主体性。
- 方法论采收型事项：把笔记、摘录、复盘或案例转化为系统原则、方法论文档、SOP、Skills、资产，或者明确的不行动决定。

## 约束

- 在检查目标正确性之前，不要优化执行。
- 不要把每份来源笔记都变成行为改变。先判断它属于阅读消化、方法论、资产、Skill/SOP、项目执行还是不采取行动。
- 当目标不清晰或资源预算不合理时，优先降级、延迟或关闭。
- 不要像优化生产任务一样优化关系、恢复或体验型事项。
- 不要默认资产化。只有模式可能重复，且提炼成本低于未来节省时才采收。
- 如果用户要求执行，把当前阶段转换成下一项具体状态跃迁，而不是完整人生规划。
- 压力较高时，扩大范围前加入休息、身体状态和缓冲检查。
- 失败成本较高时加入保障措施：安全系数、公开承诺前延迟、可逆测试、绊线或退出条件。
