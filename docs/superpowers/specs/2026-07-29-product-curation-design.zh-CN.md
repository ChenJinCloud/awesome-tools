# 产品策展设计

[English](2026-07-29-product-curation-design.md) | [简体中文](2026-07-29-product-curation-design.zh-CN.md)

## 目的

`awesome-tools` 是一个小而严格的个人产品集合，以维护者的直接体验、持续观察或可信的一手用户经验为基础。它不追求成为完整目录、书签集合或厂商广告渠道。

被收录并不自动等于被推荐。每个正式条目都会说明验证深度和证据来源。

## 范围

集合可以包含任何产品类型，包括：

- 软件以及桌面或移动应用；
- SaaS 和在线服务；
- 硬件；
- 专业或消费服务；
- 开源项目；
- 组合多个产品的工具和工作流。

产品能够进入集合，是因为它支持具体用例并满足下列证据要求，而不是因为属于某个偏好的行业或技术类别。

## 仓库结构

```text
README.md
catalog/
products/
  software/
  saas/
  hardware/
  services/
  open-source/
archive/
.github/
  ISSUE_TEMPLATE/
    suggest-product.yml
  PULL_REQUEST_TEMPLATE.md
templates/
  product-entry.md
```

- `catalog/` 保存经过审查的工具记录和高层能力或用例说明；私有实现保留在本仓库之外。
- `products/` 保存正式接纳的产品条目。
- `archive/` 保存已经不再适用或不再推荐的条目，并记录原因。
- 候选项保留在 GitHub Issues 中，不进入 `products/`。

## 状态模型

正式产品条目使用以下三种状态之一：

| 状态 | 含义 |
| --- | --- |
| `researched` | 维护者通过持续观察、可信的一手用户经验和产品一手来源形成独立判断，但尚未亲自完成核心工作流。 |
| `tested` | 维护者亲自完成了至少一个核心产品工作流，并记录环境、结果和限制。 |
| `recommended` | 维护者愿意针对明确的受众和用例推荐该产品，同时明确说明不应推荐的情形。 |

`candidate` 是 Issue 状态，不是正式 catalog 状态。常见推进路径为：

```text
候选 Issue -> researched -> tested -> recommended
```

当证据、产品质量或当前相关性发生变化时，也可以降低状态。不再符合要求的产品移至 `archive/`。

`needs-review` 是临时维护标签，不是第四种正式状态。该标签存在期间，README 不得把该条目当作当前推荐展示。

## 准入标准

产品只有满足以下全部条件才能进入 `products/`：

1. 支持一个具体且能够解释的用例。
2. 判断基于直接使用、持续观察或可信用户的具体一手经验。
3. 已通过一手来源核对产品能力、价格、可用性和平台支持。
4. 条目说明该产品相对于普通替代方案为何值得关注。
5. 明确列出重要限制、风险和不适用场景。
6. 已确认事实、第三方经验和维护者判断能够相互区分。
7. 包含验证状态和最近审查日期。
8. 披露厂商关系、赞助、联盟激励和其他利益冲突。
9. 不包含凭证、私有记录、内部 URL、私有账号标识、Cookie、会话、日志或特定机器的私有路径。

如果产品只得到营销材料、流行度、随口推荐或不完整证据的支持，它应继续停留在候选 Issue。

## 产品条目结构

每个产品使用一个 Markdown 文件，并包含以下部分：

```markdown
# 产品名称

状态：
最近审查：
产品类型：
官方网站：

## 它是什么
## 为什么值得收录
## 最适合谁
## 经验基础
## 已验证内容
## 尚未验证内容
## 优点
## 限制与风险
## 价格与获取方式
## 隐私与数据处理
## 替代方案
## 来源链接
## 披露
```

`经验基础` 为必填项，用来说明判断来自直接使用、持续观察还是可信的一手用户经验。对于 `researched` 条目，`尚未验证内容` 为必填项。

## 候选与贡献工作流

```text
发现或收到一个产品
-> 创建一个候选 Issue
-> 检查重复、范围、经验基础和利益冲突
-> 收集一手来源和可信经验
-> 拒绝、继续观察或准备正式条目
-> 每个 Pull Request 只提交一个产品
-> 运行自动格式和安全检查
-> 维护者审查
-> 合并或要求修改
```

候选 Issues 收集：

- 产品名称、官方网站和产品类型；
- 它解决的问题；
- 提交者身份及其与产品的关系；
- 值得调查的原因；
- 已有经验的来源和深度；
- 维护者或提交者是否使用过；
- 已知限制、风险和替代方案。

维护者可以直接创建候选项和条目。用户和厂商可以提交候选 Issues，但厂商自荐必须披露关系。外部提交者不能指定 `tested` 或 `recommended`，这些状态要求维护者的直接体验和判断。外部 Pull Request 每次只包含一个产品。

初期公开贡献采用 Issue 优先。只有在大约十个已接纳条目证明结构和审查标准稳定后，才应开放外部直接提交产品 Pull Request。

## 自动检查

自动化检查结构和公开安全，而不判断产品好坏。检查应覆盖：

- 必填元数据和章节；
- 允许的状态值；
- 重复的官方网站 URL；
- 失效链接；
- `最近审查` 是否存在且有效；
- 意外出现的密钥、账号标识、原始记录、日志或私有路径；
- `researched` 条目的 `尚未验证内容`；
- `tested` 和 `recommended` 条目实际完成的具体工作流；
- `recommended` 条目明确的受众、用例和不推荐边界。

检查只报告文件名和规则名，不得打印检测到的密钥值。

## 审查与维护

默认审查周期：

| 产品类型或风险 | 审查周期 |
| --- | --- |
| 稳定的软件或硬件 | 12 个月 |
| SaaS、AI 产品或快速变化的服务 | 6 个月 |
| 处理敏感数据、权限或私有工作流的产品 | 3–6 个月 |

重大改版、收购、实质性价格变化、服务关闭或安全事件会触发即时审查。

审查结果包括：

- 保留状态并更新 `最近审查`；
- 证据不完整时添加临时 `needs-review` 标签；
- 原判断不再得到支持时降低状态；
- 产品不可用、停止维护、实质退化、不再适合记录的用例，或不再值得收录时，将条目移至 `archive/`。

归档条目保留归档日期、原状态、原因、可能的替代方案，并明确提醒历史结论可能已经过时。

## 边缘情况

- 网站暂时不可用时添加 `needs-review`，而不是立即删除。
- 未确认的价格会阻止状态升级，并标记为未确认。
- 厂商声明与可信经验冲突时，保留冲突并注明来源。
- 厂商请求可以纠正事实错误，但不能推翻独立判断。
- 未验证的安全报告需要注明来源并标记为未确认。
- 含有私有数据的贡献应被清理或关闭，公开讨论中不得重复敏感内容。

## 验收标准

满足以下条件时，产品策展系统可以进入实施：

- 仓库能够区分候选项和正式条目；
- 三种正式状态都有可执行的证据要求；
- 存在可复用的产品模板和候选 Issue 模板；
- 一个产品对应一个可审查的 Pull Request；
- 自动检查覆盖结构、链接、重复、时效性和公开安全；
- README 优先展示 `recommended`，其次是 `tested`，同时清晰标记 `researched`；
- 审查与归档规则既保留历史，又不会暗示过期判断仍然有效。
